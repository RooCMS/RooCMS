## Обзор
RooCMS предоставляет RESTful API для управления контентом и данными системы. API построен на чистом PHP без использования фреймворков с использованием собственного класса `ApiHandler`.

Документация описывает текущую реализацию маршрутов в [router.php](router.php), контроллеров и вызываемых ими сервисов. Примеры содержат условные данные.

## Запросы и доступ

Базовый URL локального окружения: `https://dev.roocms.com/api`. Пути в разделах указаны относительно него. Используется HTTPS.

Для JSON-тела передавайте `Content-Type: application/json`. Загрузка файлов использует `multipart/form-data`; имя файлового поля зависит от метода.

CORS-заголовки задаются в `api/index.php`: разрешён origin `*`, методы GET/POST/PUT/PATCH/DELETE/OPTIONS и заголовки Content-Type/Authorization.

Защищённые методы принимают `Authorization: Bearer <access_token>`. Токены — непрозрачные строки; клиенту не нужно разбирать их содержимое. Сроки действия возвращаются при входе и обновлении токенов.

| Доступ в документации | Требование |
| --- | --- |
| Публичный | Токен не обязателен |
| Пользователь | Действующий access token |
| Модератор | Токен и роль `m`, `a` или `su` |
| Администратор | Токен и роль `a` или `su` |

Роли: `u` — пользователь, `m` — модератор, `a` — администратор, `su` — суперпользователь. Дополнительные проверки владельца и целевого пользователя описаны у методов.

## Ответы

Обычный успешный ответ контроллера:

```json
{"success":true,"timestamp":"2026-11-25 12:00:00","data":{"key":"value"}}
```

`message` добавляется, если метод его передаёт. При результате `null` ключ `data` отсутствует:

```json
{"success":true,"timestamp":"2026-11-25 12:00:00","message":"Profile updated"}
```

Описания результатов в разделах относятся к содержимому `data`, если явно не сказано иначе. У некоторых методов есть дополнительная вложенность `data.data`; она отражает существующий код. Корень API имеет собственную форму ответа. Методы скачивания возвращают файл.

Ошибка:

```json
{"error":true,"message":"Validation failed","status_code":422,"timestamp":"2026-11-25 12:00:00","details":{"validation_errors":{"site_name":"This field is required"}}}
```

`details` необязателен. Ошибки отдельных полей, сформированные через общий обработчик валидации, находятся в `details.validation_errors`. Не все ошибки с кодом 422 содержат этот объект: сервис может вернуть только `message`.

Неперехваченные исключения обрабатываются общим Debugger: HTTP 500 и `Content-Type: application/json; charset=utf-8`. Его JSON отличается от ошибок контроллеров: `error: "internal_error"`, `message`, `time`, `reference`; в режиме отладки — `error: "exception"` и диагностические поля.

| Код | Значение |
| --- | --- |
| 200 / 201 | Успех / создание ресурса |
| 400 | Некорректные параметры или операция |
| 401 / 403 | Необходима авторизация / недостаточно прав |
| 404 / 405 | Ресурс или маршрут не найден / метод не разрешён |
| 409 | Конфликт, например занятый email |
| 422 | Ошибка валидации |
| 429 | Превышено число попыток в операциях, где это реализовано |
| 500 / 503 | Внутренняя ошибка / недоступность сервиса |

## Пагинация и типы

Единого формата пагинации сейчас нет. Users и Media принимают `page` (по умолчанию 1) и `limit` (по умолчанию 10, ограничение 10–100). ACP Structure принимает `offset` и `limit` (50, ограничение 1–200). Backup использует собственный фильтр `limit`. Формат результата указан в соответствующих разделах.

Query-параметры, читаемые через `get_query_params()`, автоматически преобразуются из строк в числа, boolean, null или JSON. Пустые значения исключаются. Для флагов `navigation` и `published` у дерева используйте `=1`: проверяется наличие параметра после этого преобразования.

## Поддержка документации

Документация редактируется вручную вместе с согласованным изменением API. Для метода указываются путь, HTTP-метод, доступ, параметры, результат, ошибки и пример использования. Общие правила описываются здесь, особенности — в файле раздела.

Источники истины: регистрация маршрутов в `router.php`, реализация контроллера и вызываемые сервисы. При расхождении исправляется документация по фактическому поведению; изменение самого API требует отдельного согласования.

## Базовая информация
- **Базовый URL**: `/api/`
- **Формат данных**: JSON
- **Аутентификация**: JWT Bearer токены
- **Версионирование**: Через URL path (`/v1/`)
- **Архитектура**: Собственная система роутинга RooCMS с Dependency Injection

## Версии API
- **v1**: Текущая dev версия (2.0.0 alpha)

## Основные принципы
- Все запросы должны использовать HTTPS
- Все ответы возвращаются в формате JSON
- HTTP статус коды используются для указания результата
- CORS включен для кросс-доменных запросов
- Поддержка динамических параметров в URL (`{id}`, `{param}`, `{slug}`)
- JWT аутентификация для защищенных эндпоинтов
- Роль-базированный контроль доступа (RBAC)
- Middleware система для обработки запросов
- Полная валидация и санитизация данных
